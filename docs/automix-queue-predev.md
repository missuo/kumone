# AutoMix 队列重排 预研

> 状态:设计(2026-08-29) · 未写任何产品代码,待听感负责人审阅后动工
> 前置阅读:[`automix-spec.md`](automix-spec.md) · [`automix-structure-predev.md`](automix-structure-predev.md)

---

## 0. 一页摘要

**要解决的问题**:转场质量的上限由"相邻两首歌是否兼容"决定,而现在的顺序(列表序 / shuffle)对此完全随机。BPM 差 12%、调性相冲、风格断裂的相邻对,规划器只能降级到普通 crossfade——过去几周做的 tempo ramp、dominant-deck、vocal exchange 全都用不上。**表达能力已经就位,缺的是让它有用武之地的曲序。**

**方案**:一个新的队列模式(暂名 **AutoMix 顺序**,与 shuffle 互斥的第三态)。开启后,"下一首播什么"由程序决定:

1. **规划器就是打分器**。不发明第二套兼容度模型——对每个候选对直接跑一次 `TransitionPlanner.plan(A, B)`(纯函数,已存在),按它给出的转场档位打分:带 ramp 的 beatMatched > beatMatched > staged crossfade > 普通 crossfade。得分高 ⇔ 真的能做出好转场,没有代理指标失真。
2. **满意即止的贪心,不做全局排序**。分析需要完整音频,几十首的歌单不可能预先全下。候选池 = 所有已分析的剩余曲目(免费);若其中已有「够好」的候选(默认:能 beat-match)就地选定、零下载,否则按列表序指数升级补下载(1 → 4 → 16 首,轮内出现满意候选即停),直到满意、队列耗尽或 deadline。选定者喂给现有的 prefetch/arming 流水线。
3. **重排不是过滤**。每首歌都会播到:落选者带 aging 加分回到下一轮,不存在"永远轮不到的歌"。

**不做的事**:不动 gates(准入门槛照旧,曲序只是让门更常被自然通过)、不做全局 TSP、不跨歌单推荐(只重排用户给的队列)、不改引擎。

**代价**:候选按**最低码率档**下载打分(~4 MB/首,见 §2.2;胜者再按播放音质重下重分析),满意即止 ⇒ 典型每次选曲几首、免费池命中时为 0,**单次硬上限 24 首**;sidecar 落盘后是一次性成本,预热摊在整张歌单上。一次打分 = 每个已分析候选一次纯函数调用,微秒级;定下之后再免费预演 8 步给列表看。

## 1. 现状与失效模式

顺序今天由两个来源决定,都与音频内容无关:

| 来源 | 实现 | 转场视角的问题 |
|---|---|---|
| 列表序 | `activeQueue[currentIndex + 1]` | 专辑序对聆听有意义,对混音是随机的 |
| shuffle | Fisher–Yates 一次洗牌 | 均匀随机,兼容对出现率 = 底数概率 |
| playNextList | 用户手动插队 | 用户意图,必须无条件优先(维持) |

prefetch 流水线(`PlayerService` 的 `PrefetchedNext`)只认"下一首",下载、分析、规划、arming 全部围绕这一首展开。规划器拿到什么对就规划什么对——**它从没有过选择权**。

失效模式直接可量化:对一个典型混合歌单,相邻对能进 beatMatched 的比例受制于 `beatMatchBPMDeltaCap`(ramp 后 11.5%)、调性门、风格门的联合概率。随机曲序下这是碰运气;而同一批歌重排后,几乎每一步都能找到至少一个兼容候选——歌单内部的兼容对远多于"恰好相邻"的兼容对。

## 2. 方案

### 2.1 模式与交互契约

`shuffleEnabled: Bool` 升级为三态(内部表示,UI 另议):

```
enum QueueOrder { case listed, shuffled, autoMix }
```

- **互斥**:开 AutoMix 顺序即关 shuffle,反之亦然。`queue` 原始序永远保留,关掉模式即回到原序(和 shuffle 的现契约一致)。
- **playNextList 永远优先**:用户手动"下一首播"插队照常;插队曲播完后模式接管。
- **手动点歌 = 硬跳**:用户点任何歌照常立刻播,模式从新位置继续接管。
- **上屏顺序**:`upcomingTracks` 第一位是**已选定**的下一首(确定的);其后是 **provisional 预演链**(默认 8 步,`lookaheadDepth`);再其后才是原队列剩余。选定发生在 prefetch 启动时,不是播放开始时——列表在一首歌的前半段会更新一次。
  - **预演链是给人看的,不是承诺**。它只用**已分析池**做链式贪心(每步以上一步的胜者为出曲重新打分,aging / samePenalty 照算,但算在**计数器的副本**上——预演绝不能改变它所预演的未来)。到了每个 seam 的真实决策点,那一首仍然从头重选一次:那时池更大、还有 deadline,答案完全可能不同。
  - 之所以敢直接**摆进 `autoMixQueue`**,是因为它和"已选定的下一首"用的是同一招:把选择物化进列表,而不是给 `upcomingTracks` 再造一个真相来源——`currentIndex` 始终是唯一游标,链错了下一轮重新 splice 即可,自愈。
  - **但要一次性赋值**。`autoMixQueue` 是 `@Published`,队列视图是几百行,每次改动都要 SwiftUI 全表 diff 一遍。第一版一步一挪 = 一次刷新 9 次 publish、9 次全表 diff,而且每落地一个候选就来一轮——这是"队列操作之后 app 像卡死了"的直接来源。现在整个新数组一次算好、一次赋值,**顺序本来就对时干脆不赋值**(定完之后这是常态)。
  - debug panel 的 `lookahead` 行明确标 `provisional`,和确定的下一首在视觉上分开。
  - **代价必须实测,不能靠"纯函数所以很快"**。`audition order --bench`(156 首池):单次 `plan`+打分 release 0.006 ms / debug 0.088 ms;**一次 rank(整池)** release 0.9 ms / debug 13.8 ms;**一条 depth=8 的链** release 5.6 ms / **debug 109.6 ms**。链 ≈ (depth+1) × 池大小 × 单次,对池**线性**——而池已经从设计时的 4 首长到 200+。
  - 结论与做法:(1) **链在 detached task 上算**,只把答案送回主 actor;跨界的是纯值快照(`[Int: TrackAnalysis]`、id 列表、歌手 id、两个 config),不带 `Track`、不带选择器。(2) **重算被节流**:定曲(链头变了)强制重算,池长大触发的最多 5 s 一次,且同时只允许一个在飞;被超越的那个凭 generation 自己丢掉答案。(3) 落地时按当前队列重新映射 id,**已离队的步骤直接丢掉**——链是 provisional,没有"修复"这回事。
  - **超过 50 ms 的一次计算会打 journal(`order SLOW …`)**。这条不是装饰:整套设计当初是按 4 首池写的,"微秒级"这个说法在 200 首池上已经不成立,诚实的做法不是断言它便宜,而是它一旦不便宜就当场喊出来。

### 2.2 候选池与获取策略:**满意即止的指数升级(satisficing escalation)**

设剩余未播集合为 R。

**先说为什么不是固定窗口。** 初版用的是「R 前 W 首(W=4)+ 已缓存曲目」的固定窗口。在用户真实的 56 首缓存上跑 `audition order`,结果是:

| 曲序 | beatMatched 相邻对 |
|---|---|
| 原序 | 7/55(13 %) |
| 贪心 W=4 | 9/55(16 %) |
| 贪心(全部已分析) | 29/55(53 %) |

**W=4 相对原序的 3 个百分点在噪声量级内——固定窗口几乎一文不值。** 价值全部来自「候选池够大」,而不是「窗口对齐了列表序」。窗口的问题是它同时限制了两件事:花多少钱,和能看到什么;而真正该限制的只有前者。

**新策略:满意即止的指数升级。** 每次选曲:

1. **从手上已有的全部分析出发**——历次轮次买来的、上几次会话买来的、磁盘上现成的 sidecar,全部是 R 中的免费候选(零网络、零分析器)。若其中已有候选达到**满意档位**,立即选定,**本次下载数 = 0**。
2. **否则按列表序沿 R 指数升级**:下载+分析接下来 **1** 首(最低码率、并发预算 1、复用同一套抓取机制),每落地一首**立刻重新打分**;满意即停。不满意则下一轮 **4** 首,再下一轮 **16** 首,每轮 ×4,上界为三条:R、**单次选曲下载预算 `maxDownloadsPerPick`(默认 24)**、以及决策 deadline(时长 − 120 s)。**轮内一旦出现满意候选就地停止,不跑完这一轮**——省下的大头正在这里。
3. **deadline 到达 / R 耗尽 / 预算买满仍不满意**:在已分析候选里取最优(既有行为);一首都没分析出来就老实退回列表序,模式永不为了等下载而断播。

**为什么必须有单次预算。** 指数增长在长队列上不是理论无界,是实际无界:实测一首 10 分钟的开场曲在 220 首队列上跑了 5 轮、买了 177 首才被 deadline 截断——几乎整个歌单的流量,由一个 seam 买单。升级本身没做错,是没人给它上限。

**上了限也不亏**,因为买到的东西一件都不丢:这次没够到的尾巴,在下一次选曲时仍然是未解决的,而下一次是从一个刚刚**多了 24 首**的池子出发的。**预热被摊到歌与歌之间,而不是全压在第一首上**——总量一样,分布不同,而且听众不用干等着。实测(226 首,§5.1):设 24 上限后 beatMatched 反而是 162/225(72 %),不设上限是 159/225(71 %)。**上限没有代价。**

**满意档位**是 `QueueOrderConfig` 的一个旋钮,默认 **beatMatched 及以上**(ramped 与普通 beatMatched 都算满意)。

**为什么「满意即止」在这里是对的**:tier 是主项(§2.3,`tierSpacing` 保证连续项不能跨档翻盘)。一旦某候选达到满意档,再多买一轮只可能换来*更高的档*或*同档内的次序微调*——前者收益有限,后者是二阶量。为此多花几首下载、多等一分钟,是明显不划算的交易。

**升级是按 ID 集合记账、不记下标的**:frontier = 已准入集合 ∩ *当前* R。用户删歌、加歌、手动跳转,只需重新取交集——离队的曲目自然消失,新入的曲目在轮次触及它之前不被准入。

**副产品:按需预热。** 每轮买来的分析写成 sidecar 落盘(本来就会),所以下一次选曲的免费池更大、更可能零下载命中。冷启动的歌单越听越便宜,代价是一次性的。

- **打分用最低音质**。候选按最低码率档下载(~4 MB/首 vs 无损 20–40 MB),分析器本来就把输入降到 22.05 kHz 单声道,打分所需的全部信号(BPM、调性、melProfile、能量形状)对码率不敏感。**但低音质分析只产出打分,绝不进入规划**:有损编码器在文件头部引入编码延迟(MP3 常见数十 ms),整条 beat/downbeat 网格随之平移——打分的各项都是平移不变量,不受影响;beat-match 的对齐不是。胜者选定后走现有 prefetch 流水线下载**播放音质**并重新分析(1–2 s),规划/arming 全部建立在真文件的 sidecar 上。已有播放音质缓存的候选跳过低质档,直接用现成分析。
- **下载预算**:同一时刻最多 1 个候选在下载(现有 prefetch 也是 1),按升级顺序补齐;低质档一首几秒钟,分析本身 1–2 s/首,忽略不计。
- **礼让规则**:候选下载是后台工作,**播放音质 prefetch 在传输时升级暂停,传完自动继续**(进度 tick 每秒回来一次)。当前曲自己还在边下边播(未完整落盘)时同样让路。免费的那一半——磁盘扫描——不受影响,它不走网络。
- **降级**:seam deadline 到达时只在**已分析**的候选里选;一个都没有就退回"下一首"原行为——模式永远不会为了等下载而断播。
- **决策提前量 = 120 s**(`autoMixDecisionLead`,另有 `duration × 0.35` 下限)。原为 90 s = 30(重下播放音质 + 重分析)+ 60(stem 预渲染跑道);实测第一段能吃掉 40 s 以上(无损传输 + 分析器),导致预渲染只剩不到 50 s、stem 手法悄悄退回整轨 crossfade。120 s 是同一套算式换上实测数字。
  注意这是**最坏情况**:只有走 deadline 的选曲才等这么久。满意即止 / 队列耗尽 / **预算买满**三种收口都是一到就定,暖池上往往是开播几秒内就定下了——**单次预算因此顺带把"定得晚"也一起治了**。
- **模式关闭 ⇒ 什么都不实例化**:`PlayerService` 把选择器持有为 optional,`.listed` / `.shuffled` 下走的是原来那条字节相同的路径,不分配、不打分、不发请求。

### 2.3 打分

对当前曲 A 与每个已分析候选 B,跑 `TransitionPlanner.plan(A, B)`(含 gate trace),得:

```
score(B) = tier(plan)                        // 主项,档位间距拉大
         + w_tempo · tempoAffinity(A, B)     // 档位内排序,BPM 比值越近 1 越高
         + w_key   · keyAffinity(A, B)       // Camelot 距离(同调/邻调/平行调),置信度加权
         + w_style · melCosine(A, B)         // 风格指纹余弦(规划器风格门同款信号)
         + w_energy· energyContinuity(A, B)  // 出点段能量 vs 入点段能量,惩罚硬跌落
         + aging(B)                          // 每落选一轮 +ε,保证不饿死
         − samePenalty(B)                    // 同歌手紧邻连播的轻惩罚(可关)
```

**未来富余项(`w_future · futureRichness`,默认关)。** 贪心天生近视:它买下眼前最好的 seam,从不问这一步给后面留下了什么。实测(§5.2)这一点是可见的——101 个 seam 的排程里 beatMatched 的分布是 **89 % / 59 % / 32 %**,兼容对在前三分之一就被吃光,尾部只剩 aging 强行逃离聚簇。于是加了第五个连续项,估计「选它之后还剩多少可接的曲目」:

- **(a) degree**:以候选为出曲,数剩余池里还有多少首能进满意档,除以池大小。每个候选一次 rank。
- **(b) rollout**:从候选出发按同一套贪心往前走 `futureRolloutDepth`(默认 3)个 seam,取这几步档位的均值归一化。每个候选 `depth` 次 rank。

两条都只对**排名前 `futureTopK`(默认 5)**的候选计算,且评估池被 `futurePoolCap`(默认 64,超出等距抽样)封顶——这两个数是主 actor 上的价格闸。加分**非负且只发给最好的 K 个**,所以它能重排队首,却不可能把一个候选压到它本来就赢过的候选之下。

- **tier 是主项**,连续项只在同档位内排序——绝不让"风格很像的 crossfade"赢过"能 beat-match 的对"。未来项也在这条线之内:`futureWeight` 上限 2,连同其余四项共 6,仍远小于 `tierSpacing` = 10。**当前 seam 永远不会为了更好的未来被卖掉**,这是一条测试而不是一句承诺。
- 连续项全部来自 `TrackAnalysis` 现有字段(`bpm`、`keyPitchClass/keyIsMinor/keyConfidence`、`melProfile`、`sections` 能量、`referenceLoudness`),**零新分析**。
- 权重进 `TransitionPlanner.Config` 同级的一个 `QueueOrderConfig`,吃现有的 `audition sweep` 归因机制。

### 2.4 决策流水线(全部挂在现有钩子上)

```
当前曲开始播放
  → 组候选池,按序补下载(预算 1)
  → 每个候选文件落地即分析(现有 TrackAnalyzer,sidecar 复用)
  → prefetch 时点(现有逻辑触发处):对已分析候选打分,取最高
  → 选定者进入现有 PrefetchedNext → 规划 → arming → 预渲染,一字不改
落选者:留在 R,aging +ε,已下载的音频/分析躺在缓存里等下一轮(边际成本一次性)
```

唯一改动点是"`currentIndex + 1` 换成 `selector.pick()`",发生在 `PlayerService` 的队列层;引擎、规划器、渲染链路零感知。

### 2.5 可观测性

- **debug panel 加一节**:候选表(曲名 / tier / 各分项 / 总分),当前选择高亮——听感上"为什么接这首"当场可查。另有 `escalation`(第几轮 / 已买几首 / 上限)与 `lookahead`(预演链,明确标 `provisional`)两行。
- **`PlaybackJournal`**:轮次开启、每次抓取成功/拒绝(带原因)、收口(带 reason=satisfied|deadline|exhausted|budget 与计数)、预算买满、预渲染的晚启动与跑道不足拒绝——全部落日志。这些行不是装饰:模式静默退化成列表序那次排查之所以靠猜,正是因为当时一行都没有。
- **`audition order` console 命令**(验收工具,先于产品代码写):输入一个歌单的本地曲目集合,输出四条排程的 planner tier 分布对比 + 完整排程——原序 / 贪心 W=4 / **升级(出货策略)** / 贪心(全部已分析,即天花板)。不用耳朵先用数字回答"重排到底多有用"。
  - 升级那一条是**带价格的**:它模拟「分析按升级顺序才变可见」(否则离线全缓存会让每次选曲都免费,毫无意义),报告**每次选曲的平均/最大下载数**、轮数上界、以及有多少次选曲是「达到满意档而停」而非「队列耗尽」。可见性跨选曲保留,因为 sidecar 就是这样落盘的——预热的收益因此也在数字里。
  - **每一行都按三分之一报**(前 / 中 / 后)。总占比是个平均数,而它平均掉的正好是本模式最真实的失效形状:贪心在池子还满的时候把兼容对花光,尾部只剩 aging 强行逃离聚簇。一个百分比看不出这件事,三个能。§5.2 的否定结论就是靠这三个数得出的。
  - 唯一没建模的是 deadline(那是一个时钟,离线无意义),所以那里的下载数是 deadline 会截短的**最坏值**,不会低报。

## 3. 不做的事

- **全局排序优化**(TSP/beam search 全歌单):需要全量分析,首播延迟不可接受;贪心 + aging + 满意即止升级已经拿到了「全缓存贪心」这个天花板的全部收益(实测 56 首:升级 31/55 vs 全缓存贪心 29/55,见 §5.1),再做全局优化没有余量可取。
- **跨歌单推荐/补歌**:只重排用户已给的队列,不添加内容。
- **放松 gates**:曲序解决"没得选",gates 继续把关"选了也不行"。两层各司其职。
- **UI 大改**:第一版一个开关 + upcoming 第一位如实显示,不做拖拽解释性 UI。

## 5. 验收

1. `audition order` 对真实缓存输出:beatMatched 对占比 原序 vs 重排,预期显著提升(这是本功能存在的意义,量化交付)。

   **§5.1 实测(用户缓存,2026-08-29)**。第一轮 56 首时:原序 7/55(13 %)、贪心 W=4 9/55(16 %)、升级 31/55(56 %)、全缓存贪心 29/55(53 %)。**W=4 相对原序的 3 个点在噪声量级内,固定窗口就是在这里被废弃的。**

   一次真机连听把缓存暖到 226 首后重跑:

   | 排程 | beatMatched | 代价 |
   |---|---|---|
   | 原序 | 17/225(8 %) | — |
   | 贪心 W=4 | 45/225(20 %) | 固定窗口,已废弃 |
   | **升级 ≤24/次(出货策略)** | **162/225(72 %)** | 平均 **1.00** 首下载/次选曲,最贵一次 24 首(= 上限),≤4 轮;72 % 的选曲达到满意档而停,只有 6 次撞到预算 |
   | 升级 ≤256/次(等价于不设限) | 159/225(71 %) | 最贵一次可以买到三位数 |
   | 贪心(全部已分析) | 159/225(71 %) | 需要整个歌单预先分析完 |

   三件事:

   1. **单次预算不要钱**。设 24 上限反而比不设限高一点(162 vs 159)——上限只改变**买的节奏**,不改变**能选的池**,而池是靠 sidecar 跨选曲累积的。
   2. **升级追平并略胜全缓存贪心**(162 vs 159),却不需要"整个歌单预先分析完"这个前提。停在「够好」上让 aging 的轨迹不同,而 aging 本来就是防饿死项、不是画质项。
   3. **平均 1.00 首/次选曲** = 冷缓存下把这批歌各买了一遍。这正是一次性成本的形状:第二遍听同一批歌,免费池已经满了,大量选曲是零下载命中。
   **§5.2 未来富余项(regret):否定结论,不出货(2026-08-29)**

   验收口径是**最后三分之一的 beatMatched 占比**——总分是个平均数,而平均数正好把尾部塌陷抹掉。`audition order` 因此每一行都加报三分之一切分,并用 `--order-set futureMode=1|2,futureWeight=…` 做 ON/OFF 对照。出货那一行(升级 ≤24/次)的基线就是本节要打的靶子:**89 % / 59 % / 32 %**。

   跑了**两轮**,因为中途用户的 app 还在听歌、缓存自己从 112 首长到了 137 首。两轮各自内部一致(第二轮用软链接把语料冻住再跑),但**彼此不一致**,而这恰恰是结论:

   **第一轮** — 112 首缓存的 5 个前缀(n=45/60/75/90/112,377 个 seam):

   | 设置 | 总计 | 前 1/3 | 中 1/3 | **后 1/3** |
   |---|---|---|---|---|
   | **关(出货)** | 227/377(60.2 %) | 85.4 % | 63.0 % | **33.1 %** |
   | degree w=2.0 | 235/377(62.3 %) | 85.4 % | 68.5 % | **33.9 %** |
   | rollout w=2.0 | 243/377(64.5 %) | 87.0 % | 74.0 % | **33.1 %** |

   **第二轮** — 冻结的 137 首缓存的 4 个前缀(n=60/90/120/137,403 个 seam):

   | 设置 | 总计 | 前 1/3 | 中 1/3 | **后 1/3** |
   |---|---|---|---|---|
   | **关(出货)** | 268/403(66.5 %) | 89.4 % | 80.0 % | **30.9 %** |
   | degree w=2.0 | 268/403(66.5 %) | 88.6 % | 77.0 % | **34.6 %** |
   | rollout w=2.0 | 272/403(67.5 %) | 96.2 % | 78.5 % | **28.7 %** |

   四件事:

   1. **验收不通过,两种设计都是**。degree 的尾部两轮分别是 +0.8 和 +3.7 个点,方向一致但很小,而且第二轮是从中段搬过来的(中段 −3.0);rollout 的尾部两轮是 0.0 和 **−2.2**,方向都不一致。**没有一个能复现的、材料级的尾部改善。**
   2. **总分上的"收益"也不复现**。rollout w=2.0 第一轮把总占比抬了 4.3 个点,第二轮只有 1.0 个点;degree 第一轮 +2.1,第二轮 0.0。两轮之间唯一稳定的是 rollout 把前三分之一推到 96 %——**它让前段更前载,正好是问题的反面**。
   3. **为什么尾部动不了**。最后三分之一里池从 ~45 首缩到 1 首,最后一对根本无从选择。「偏好枢纽曲目」不改变枢纽终究会被花掉这件事;真要救尾巴只能**主动为它留货**,即明确牺牲前段的 seam 质量。那是一个产品决定(要不要让开头差一点换结尾好一点),不是一个打分项能顺手做的事,也不该由一个 in-tier 权重偷偷做。
   4. **代价单**(`--bench`,111 首池,K=5、cap 64):degree 主 actor 上 release +1.9 ms / debug +23.8 ms(一次 pick 共 32.7 ms,压线通过 50 ms 警戒);rollout release +4.5 ms / **debug +86.7 ms(一次 pick 96.1 ms,直接撞线)**——质量上稍好的那一种,恰恰是必须搬去后台才能用的那一种。

   **因此不出货**:`futureMode` 默认 `off`,活的选曲与本项存在之前逐位相同(`applyFuture` 在 mode=off 时第一行就返回)。两种估法、五个旋钮、`--bench` 的 future 行与三分之一报表全部留在原地,任何人 `--order-set futureMode=1` 一行即可复现上表——**留下的是测量能力,不是一个只会加噪声的权重。**

   **因此不出货**:`futureMode` 默认 `off`,活的选曲与本项存在之前逐位相同;两种估法、旋钮、bench 与三分之一报表全部留下,任何人 `--order-set` 一行即可复现上表。代价实测(`--bench`,111 首池,K=5、cap 64):degree 主 actor 上 release +1.9 ms / debug +23.8 ms(一次 pick 共 32.7 ms,压线通过 50 ms 警戒);rollout release +4.5 ms / **debug +86.7 ms(一次 pick 96.1 ms,直接撞线)**——赢在质量的那一种,恰恰是必须搬去后台才能用的那一种。这也是「不出货」之外的第二个理由。
