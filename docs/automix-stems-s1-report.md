## 0. 先说清楚这份报告能回答什么

S1 的 kill gate 是两个问题：

① **B 是否明显好听于 A？** — 这是**人耳盲听题**，只能由你在听完 24 个 A/B 文件之后回答。本报告不代替这个判断，也不假装做过。下面给的是**每组该听什么、预期差异在哪、以及客观测得的差异幅度**，用来让盲听更有效率。

② **solo 暴露时残留是否可接受？** — 这一半我能给出有实测支撑的答案，见 §4。结论是：**分档可接受**，且残留几乎全部落在 200 Hz–4 kHz 中频，这恰好是最难被新伴奏掩蔽的频段。

另外 S1 顺带把预研 §10 待验证清单里的第 5、6 条（端上耗时与内存）从"推测"变成了实测——虽然是在 MLX 而非 Core ML 上，见 §3。

## 2. A/B 是怎么做公平的

每组过渡对的 4 个渲染共享**同一个出点、同一个入点、同一个 overlap 长度、同一个变速比、同一个响度匹配、同一个输出增益**。前 20 s（出曲）与后 20 s（入曲）逐样本完全相同，差异**只存在于中间的 overlap 窗口**。

- **A 侧（对照）**：等功率 crossfade + 200 Hz 分频的低频交接（出曲低频在中点前收干净，入曲低频在中点接上）——即今天引擎 `stagedEQ` + `bassSwapAt` 的离线近似。**filterSweep / echoOut 没有建模**，所以 A 侧代表的是引擎的"crossfade + 低频交接"这一档，不是它的全部本事。
- **切点**：用 sidecar 里分析器真实算出的 `downbeats` / `phraseBoundaries` / `introEnd`，出点取出曲末段的一个小节线（偏向乐句边界），入点取 `introEnd` 之后第一个小节线。overlap 取出曲速度下的整小节数，钳在 10–15 s。
- **变速**：入曲用 `ffmpeg atempo` 做一次常数变速对齐 BPM。所有 6 组的 BPM 差都在 **±1.5 %** 以内，变速本身不该被听出来。

**一个必须说明的方法学决定**：出点选择是**看着分离出的人声曲线选的**——候选小节线里要求 overlap 窗内确实有人声。第一版没这么做，结果 6 组里有 2 组的切点落在纯伴奏 outro 上（`pair5` 出曲人声/混音 RMS 比只有 0.049），4 个渲染几乎一模一样，A/B 无意义。

这不是作弊：**stem 手法在纯伴奏 outro 上本来就无定义**，一个 stem-aware 的 planner 必然会做同样的选择（这正是预研 §7.5 说的"先消费 `vocalActivity`"）。而且切点对 A 和 B 是同一个，不偏袒任何一侧。但它带来一个真实的产品含义，写在 §6 的风险里：**这些歌的 outro 相当一部分是没有人声的**，stem 手法的可用率没有想象中高。

## 3. 实测成本（M4 基础款）

| 指标 | 实测 |
|---|---|
| 模型下载体积 | **64.3 MiB**（单个 safetensors） |
| 模型加载（权重就绪，进程内） | **0.42 s** |
| **30 s 片段分离（冷，含 Metal kernel 首次构建）** | **9.22 s** |
| 30 s 片段分离（热，3 次） | **9.17 / 9.15 / 9.08 s** |
| realtime factor | **约 3.3×** |
| MLX 分配器峰值 | **1.80 GB** |
| 进程峰值 RSS | **0.37 GB** |
| 一次过渡的总分离成本（出曲窗 + 入曲窗，各约 32 s） | **约 19–21 s** |

**读法**：

1. **冷热几乎没有差别**（9.22 vs 9.08 s）。MLX/Metal 这条路上没有 whisper.cpp 那种"首跑显著慢"的现象。**这条对 Core ML 不成立**——预研 §4.2 说的 ANE 首次编译开销仍需在 S2 实测。
2. **rtf 3.3× 远低于预研 §4.1 引用的 demucs-mlx 的 73×**。差异来源是模型不同（RoFormer 全是 attention，而那个数字是 htdemucs）+ 机器不同（M4 基础款 vs M4 Max）。**预研 §4.2 里"MLX 路径 30 s 片段约 0.4 s"的外推，对 RoFormer 是偏乐观约 20 倍的。**
3. **但结论不变**：一次过渡约 20 s，仍然稳稳在 60 s 预算内。预研 §4.3 的"最慢的方案也够用"依然成立，只是余量比预想的薄。**Core ML 路径若比 MLX 慢 2–3 倍（预研 §4.2 的推测方向），就会逼近 40–60 s，余量会紧张。这是 S2 需要早测的一条。**
4. **内存值得警惕**。MLX 分配器峰值 **1.80 GB** 处理 8 s chunk，比预研 §4.4 引用的"BS-RoFormer 13.35 s chunk MLX 2.7 GB"同量级，但远高于预研自己的推测（"30 s 片段 60–100 MB 激活"）。**预研 §4.4 那条推测是错的，低估了一个数量级以上。** 桌面没问题，但预研 §4.6 关于 iPhone 的"内存不是瓶颈"需要重新评估。

### 顺带：许可干净的小模型是不是质量瓶颈？

拿同一批窗口跟 [`mlx-community/mel-roformer-kim-vocal-2-mlx`](https://huggingface.co/mlx-community/mel-roformer-kim-vocal-2-mlx)（Kim Vocal 2，456 MB，仓库同样标 MIT，预研 §2.4 里 SDR 10.98 那档）对跑：

| 窗口 | zfturbo v1（64 MB） | Kim Vocal 2（456 MB） |
|---|---|---|
| pair1 | 残留 −21.4 dB | −19.3 dB |
| pair3 | 残留 −30.2 dB | −29.4 dB |
| pair6 | 残留 −25.5 dB | **−31.0 dB** |
| rtf | 3.3× | 2.5× |
| MLX 峰值 | 1.80 GB | 2.05 GB |

（残留定义见 §4；pair1 两者的 duty cycle 差得多，那一行不可直接比。）

**读法**：小模型在两个窗口上跟大模型差距在 1 dB 内，只在最难的 pair6 上明显落后（5.5 dB）。**67 MB 的许可干净选项不是明显的瓶颈**，用 7 倍体积换的是"难例上更稳"，不是"整体上更好"。预研"vocals-only Mel-Band RoFormer 是性价比最优点"（§2.4）这个判断，实测支持。

## 4. 残留：solo 暴露时听到的是什么

`pairN_out_vocals.wav` 是分离出的人声 stem，未加任何处理。客观指标（50 ms 帧，"gap" = 该 stem 自身峰值 20 % 以下的帧，残留取 gap 帧 RMS 中位数）：

| 组 | duty | 残留相对本 stem 峰值 | 残留相对同段混音 | 残留频段分布 <200 Hz / 200 Hz–4 kHz / >8 kHz | 判读 |
|---|---|---|---|---|---|
| pair1 | 44 % | **−21.4 dB** | −15.6 dB | 13 / 61 / 11 % | 残留明显 |
| pair2 | 41 % | **−32.4 dB** | −33.3 dB | 0 / 96 / 2 % | 干净 |
| pair3 | 70 % | **−30.2 dB** | −28.6 dB | 24 / 70 / 2 % | 干净 |
| pair4 | 73 % | **−17.2 dB** | −18.0 dB | 6 / 94 / 0 % | 残留明显 |
| pair5 | 74 % | **−22.3 dB** | −19.9 dB | 7 / 82 / 8 % | solo 时听得见 |
| pair6 | 52 % | **−25.5 dB** | −16.9 dB | 40 / 57 / 2 % | solo 时听得见 |

**这个指标的诚实说明**：duty 高（pair3/4/5 约 70 %+）时，"gap" 帧里混进的是唱句里的弱音，不是纯静音，残留值会被抬高。所以**这张表用来排序，不能当绝对值**。真正的判据是用耳朵听 `out_vocals`。

**三条有把握的结论**：

1. **残留是中频的，不是高频嘶声。** 6 组里有 5 组的残留能量 57–96 % 落在 200 Hz–4 kHz。这不是"镲片洗白"那种容易被忽略的 artifact，而是**旋律性乐器的糊影**——钢琴、弦乐、合成 pad 的残影。在 acapella-over 里，它要跟入曲的伴奏在同一频段争位置，**最难掩蔽**。
2. **残留幅度跟出曲的人声密度强相关。** 人声密的（pair2/3，人声/混音 RMS 0.25–0.47）残留 −30 dB 量级；人声稀的（pair4，0.14）残留 −17 dB。频谱图上 pair4 的"人声" stem 看起来根本不像人声乐句，而是连续的 4 kHz 以下谐波带 + 打击乐竖条——模型在没人声的地方把旋律乐器当人声抽了出来。**这直接给出一条产品规则：人声密度低于某个阈值就不要升级到 stem 手法。**
3. **低频残留可以廉价处理掉。** pair6 有 40 % 残留在 200 Hz 以下（贝斯漏音）。原型里 acapella 分支已经对人声 stem 加了 100 Hz 高通——这是标准 DJ 手法，顺手把这类残留清掉。中频残留没有这种便宜的解法。

## 5. 6 组 A/B：每组该听什么

所有文件在 scratchpad `stems-ab/`。听法：`A_baseline` 与某个 `B_*` 连着播，注意中间 11–13 s；然后单独播 `out_vocals`。

客观差异幅度（overlap 窗内 `A − B` 的 RMS，相对 A 的 RMS；越接近 0 dB 差异越大）：

| 组 | 出曲 → 入曲 | BPM | overlap | 出/入人声密度 | acapella | instrumental_out | vocalduck |
|---|---|---|---|---|---|---|---|
| **pair1** | `20963188` → `526439257` | 87 → 88 | 11.0 s (4 小节) | 0.38 / 0.39 | **−3.7 dB** | −11.9 | −15.3 |
| **pair2** | `2648334276` → `1308782023` | 115 → 116 | 12.5 s (6) | 0.25 / 0.39 | −4.8 | −14.8 | −17.3 |
| **pair3** | `1960619635` → `1322132356` | 120 → 120 | 12.0 s (6) | 0.47 / 0.37 | **−7.9** | −8.0 | −11.2 |
| **pair4** | `2675127419` → `20943184` | 110 → 112 | 13.1 s (6) | 0.14 / 0.23 | −3.2 | −17.4 | −20.5 |
| **pair5** | `1824918479` → `1997293311` | 132 → 130 | 12.7 s (7) | 0.40 / 0.15 | −3.7 | −9.7 | −12.6 |
| **pair6** | `553543175` → `1816189151` | 168 → 168 | 11.4 s (8) | 0.55 / 0.02 | −6.8 | **−5.8** | −8.9 |

（缓存文件没有可用的 title/artist 标签，只能用 trackID 指代。"人声密度" = 该窗口内人声 stem 与混音的 RMS 比。）

**逐组的听点**：

- **pair1（慢歌，双方都有人声）** — 最典型的"人声撞车"场景。A 侧应该能听到两个主唱同时在唱。重点听 `B_vocalduck` 有没有把这个问题解决掉。但**这一组的残留是明显档（−21.4 dB，13 % 在低频）**，`B_acapella` 很可能暴露 artifact。**这组是残留判断的关键样本。**
- **pair2（中速，分离最干净的一组）** — 残留 −32.4 dB，96 % 中频。如果连这一组的 `B_acapella` 都能听出糊，那 kill gate ① 基本可以判负。**这组是"上限"样本。**
- **pair3（120 BPM，出曲人声最密、入曲人声稀）** — acapella-over 的**最有利场景**：出曲有饱满的人声，入曲几乎是纯伴奏进来，没有争夺。差异也最大（−7.9 dB）。**如果 stem 方向有价值，最该在这一组听出来。**
- **pair4（出曲人声稀 → 入曲人声密）** — 反面样本。出曲人声密度只有 0.14，"人声" stem 大半是被误抽的旋律乐器（见 §4）。**预期 `B_acapella` 在这组会难听**，这正好用来验证"人声密度阈值"这条规则的必要性。`B_instrumental_out` 在这组反而应该合理。
- **pair5（132 BPM，flac/flac，出曲人声强）** — 中速偏快的 acapella-over 样本，残留中档。
- **pair6（168 BPM，出曲人声很密 → 入曲纯器乐 intro）** — acapella-over 与 instrumental_out 差异都大。注意这组残留 40 % 在低频，但 acapella 分支的 100 Hz 高通应当已经处理掉；对比 `out_vocals`（未处理）与 `B_acapella`（已高通）能直接听出这一步的作用。

**拼接点检查**：所有 24 个渲染在两个拼接点上的样本跳变，相对该文件自身 99.99 分位跳变的比值都在 **0.01–0.43** 之间（远低于 1.0）——即拼接处的不连续量比正常节目瞬态还小，**没有爆音**。峰值全部 ≤ 0.89，无削波。36 个文件 `afinfo` 全部通过，`afplay` 解码正常。

## 6. 我的建议：**附条件继续**，但先做 S0

**理由分四条，按重要性排序。**

### ① 决定性的那一条：S1 揭示了一个比"分离质量"更前置的瓶颈

原型跑下来最强的信号不是"分离好不好"，而是：**用户曲库里相当一部分歌的 outro 没有人声。** 第一版切点选择（纯按乐句 + 小节线，不看人声）产出的 6 组里有 2 组落在纯伴奏段上，stem 手法在那里完全无从谈起。

这意味着即使 S2/S3/S4 全部做成，**stem 手法的实际触发率会被"出曲 outro 有没有人声"这个前置条件砍掉一大截**——而判断这件事**根本不需要分离模型**，`TrackAnalysis.vocalActivity` 已经算好了，只是 `TransitionPlanner` 还没消费它（预研 §1.1 的"最低垂的果子"）。

**所以 S0 不只是"顺序上排在前面"，它是 stem 方向的前置依赖。** 没有可靠的人声活动曲线，stem 手法连"该不该升级"都判断不了。建议：**先做 S0（1–3 天），拿它在真实曲库上量一下"outro 有人声的过渡"占比。如果这个比例很低（比如 < 30 %），S2 的 2–3 周投入就失去了大部分理由，无论分离质量多好。**

### ② 残留是"分档可接受"，不是"普遍可接受"

§4 的数据很清楚：人声密的曲目残留 −30 dB 量级（大概率可接受），人声稀的 −17 dB 且残留是中频糊影（大概率不可接受）。这跟预研 §9 的对策完全对得上——**acapella-over 必须限制在高人声密度 + `tier == .compatible` 的曲目上**，其余只做 ducking / instrumental-out 这类"残留被伴奏掩蔽"的手法。

好消息是这条限制**可以用已有的信号执行**（vocalActivity + 分离后实测的 stem 能量比），不需要额外模型。

### ③ 三种手法的价值不是均等的，而最有价值的那个不需要分离

- **`vocalDuck`** 在 6 组里客观差异最小（−9 到 −20 dB），因为它只是把出曲人声压了 9 dB。但它解决的是最常见的实际问题（人声撞车），**而且预研 §7.1 说得对：ducking 只需要一条 0–1 的人声活动曲线，不需要分离。** 用现有 EQ 的中频参数带做一个近似版就够了——这是 S0 的内容。
- **`instrumentalOut`** 需要分离，但残留被自己的伴奏掩蔽（人声被抽掉，剩下的是原伴奏），**对分离质量最不敏感**。这是 stem 方向里性价比最高的手法。
- **`acapellaOver`** 是唯一真正"值回 2–3 周工程"的手法，也是唯一对残留高度敏感、且受"outro 有没有人声"限制最狠的手法。**整个 stem 方向的价值几乎全押在这一个手法上。**

### ④ 成本侧没有惊喜，但比预研估的紧

64 MB 权重、20 s/次过渡、60 s 预算——预研 §4.3 的判断成立。但 rtf 只有 3.3×（预研外推的约 1/20），内存峰值 1.8 GB（预研推测的 20 倍以上）。**桌面完全没问题；iPhone 需要重新评估**，预研 §4.6 的"内存不是瓶颈"这条应当划掉重测。

### 具体建议的执行顺序

1. **立刻做 S0**（1–3 天，独立有收益，零风险）。同时用它量一个数：**真实曲库里"出曲 outro 有人声"的过渡占比**。
2. **发一封邮件**给 ZFTurbo 确认 v1.0.0 release 资产的许可（§1）。成本一封邮件，关掉整个方向唯一的红线风险。
3. **读一遍 [`xocialize/mel-roformer-mlx-swift`](https://github.com/xocialize/mel-roformer-mlx-swift)**（MIT，0 star，2026-07 更新）。当参考实现读，不当依赖。如果它的前向确实完整，S2 最贵的那块（Core ML 的 iSTFT + MHA 改写，预研 §3.1/§3.3）有可能整块绕过去。成本半天，可能省下两周。
4. **拿第 1 步的数字 + 本报告的盲听结果，再决定 S2。** 如果 outro 人声占比高且 pair2/pair3 的 `B_acapella` 明显更好听 → 继续 S2；如果占比低，或者 pair2（最干净那组）都听得出糊 → **终止 stem 方向，把 S0 做扎实即可**。

## 7. S1 没有覆盖的东西

| 项 | 原因 |
|---|---|
| **`stagedStemSwap`（先鼓后贝斯）** | vocals-only 模型只能出 vocals / instrumental 两轨，做不了。要验证它必须先解决 htdemucs 权重许可（预研 §2.1 的红线）。**S1 对这个手法没有任何信息量。** |
| **`filterSweep` / `echoOut` 作为 A 侧对照** | A 侧只建模了 crossfade + 低频交接。**这意味着真实引擎的 A 侧比这里的 A 侧更强一点**，B 的优势被高估了一点点。 |
| **Core ML 转换可行性** | S1 用 MLX Python，完全绕开了预研 §3.1 的 iSTFT 和 §3.3 的 MHA trace 问题。**这两个 S2 的最大风险，S1 一个都没触碰。** |
| **`AVAudioEngine` offline 渲染速度**（预研 §10 第 3 条） | 本原型用纯 numpy 混音，没有验证这条。 |
| **fp16 对 SDR 的影响**（预研 §10 第 7 条） | 用的就是 fp16 权重，没有 fp32 参照可比。 |
| **iPhone 实测** | 没有测。§3 的内存数据让这件事比预研估计的更可疑。 |
